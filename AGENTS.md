# About

`docs-digger` is a standalone CMake C++ tool built on Clang LibTooling. It parses the overlunky sources
(given as an input path together with their `compile_commands.json`) and extracts the Lua API into a structured
data file. It replaces the regex-based extraction in overlunky's `docs/parse_source.py`. See `README.md` for the
toolchain setup.

## Repository Orientation

- `.agents/01-plan.md` is the work plan: technology choice, data model, extraction passes and steps.
  Work through the steps (section 6) in order and check items off (`[x]`) as they are finished. A step
  is finished only when its definition of done and the common one for all steps are both met. Then move it out
  of the plan into `.agents/00-finished.md` as one compact bullet, keeping its discoveries in the plan.
- Guiding rule from the plan: write as little code as possible. Use Clang LibTooling, AST matchers and LLVM
  support libraries (`llvm::json`, `llvm::Regex`, `llvm::cl`) for everything they can do; write custom code only
  for the sol2-specific binding patterns. Do not add third-party dependencies that LLVM already covers.

## Tools

- The host has CMake, Ninja, Git, Python, Visual Studio (MSVC STL, Windows SDK, vcvars64) and LLVM in
  `C:\Program Files\LLVM\bin` (clang-cl, same LLVM major as the pinned development package).
- The Clang/LLVM development package (static libraries and CMake configs) is pinned in `cmake/LLVMPackage.cmake`
  (`DOCS_DIGGER_LLVM_VERSION`) and unpacked into `thirdparty/` on the first configure. The Clang C++ API is not
  stable across majors: bump the pin only on purpose, together with the analyzer pins in
  `tools/requirements-quality.txt`.
- There is Lua installed on the dev host with luacheck (no shortcut) use it to check quality of Lua
  API files output.
- Use the scripts; they enter the Visual Studio environment themselves (`tools\dev-env.cmd`):
  - `build.bat [Debug|Release|All]`: clang-cl + Ninja Multi-Config in `build/digger`;
  - `test.bat [Debug|Release|All]`: build + CTest; `set DD_UPDATE_GOLDEN=1` rewrites the golden files;
  - `dig.bat [docs-digger options]`: configures overlunky into `build/overlunky` (compile database only) and runs
    the Release digger over it. A full run takes about 2.5 minutes, so iterate on fixtures and use it for
    parity checks;
  - `site.bat [generator] [json]`: builds the HTML reference from the digger JSON with `src/html/<generator>/`
    (default `starlight`) into `build/site/<generator>` and checks it (links, old anchors, search samples of
    `tools/site_samples.json`). Node.js is pinned in `cmake/NodePackage.cmake` and the packages by the generator's
    lockfile, both under `thirdparty/`;
  - `quality.bat [changed|all]`: the quality gate (see below). It creates `thirdparty/venv-quality` with the pinned
    analyzers (clang-format, clang-tidy, Lizard) and a configure-only Ninja + clang-cl build in `build/quality`.
- CI (`.github/workflows/dig.yml`) only runs by hand for now; keep it in step with the scripts.
- Downloaded tools and libraries go under `thirdparty/` (git-ignored, `THIRDPARTY_DIR` in CMake), pinned by version
  and SHA256 where the source offers one. `build/` holds only output regenerated by a configure and build: nothing
  of value is stored there, and deleting it must never force a download. For `FetchContent`, set `SOURCE_DIR`
  to `${THIRDPARTY_DIR}/<name>-<version>`, so only the build trees stay under `build/`.
  In batch scripts never `exit /b` inside a `( )` block: cmd loses the exit code there; use `goto`.

## C++ Standard

- C++23 (`CMAKE_CXX_STANDARD 23`, required, no extensions). It is supported by MSVC/clang-cl on Windows and by
  the stable Linux toolchains: GCC >= 14 and Clang >= 19 (Debian 13, Ubuntu 24.04 with `g++-14`, Ubuntu 26.04).
- Ubuntu 24.04's default GCC 13 lacks parts of the C++23 library (`std::print`, `std::ranges::to`); Linux builds
  need GCC 14+ or Clang with libstdc++ 14+. Do not use C++26 features: no stable toolchain supports them fully.
- Prefer standard library facilities that all three standard libraries (MSVC STL, libstdc++, libc++) ship. When
  LLVM already offers an equivalent that the surrounding code uses (`llvm::StringRef`, `llvm::SmallVector`,
  `llvm::Expected`), follow the surrounding code.

## Code Quality

These rules hold at all times, not only before a release.

- **Formatting.** All C++ code under `src/` and `tests/` is formatted with `.clang-format` at all times. Format
  every file you touch before you finish:
  `thirdparty\venv-quality\Scripts\clang-format.exe -i --style=file <files>`. Do not reformat unrelated files.
  `tests/fixtures/` is exempt: fixtures imitate overlunky sources and their line numbers are part of the golden
  outputs.
- **Complexity.** Cyclomatic complexity limit is 10 for every function: Lizard CCN <= 10 and clang-tidy cognitive
  complexity <= 10. Split a function instead of raising the limit. AST matcher callbacks tend to grow `if`
  chains: move each pattern into its own small function.
- **clang-tidy.** `.clang-tidy` enables `clang-analyzer-*`, `bugprone-*`, `performance-*` and
  `readability-function-cognitive-complexity`, with warnings as errors.
- **HTML generators.** `src/html/` is not C++ and the gate skips it. Keep each generator self-contained in its
  directory (inputs: the JSON, the examples, the staged downloads); data another generator would need too belongs in
  the JSON or in `tools/`. Every component, page and helper gets a one-line intent comment, as C++ code does.
- **Gate.** Before each commit run `quality.bat` (changed files plus translation units that include a changed
  header). Run `quality.bat all` once per finished step or every 20 commits, whichever comes first.
  clang-format, Lizard and clang-tidy must all pass; do not raise thresholds or add suppressions just to pass.
- Findings located in the standard library, the Windows SDK or LLVM/Clang headers cannot be fixed here and may be
  ignored: disable the check in `.clang-tidy` with a comment naming the header and the reason. Findings in our
  own code are always fixed.

## Testing

- Tests run through CTest (`ctest --test-dir <build dir> -C <config> --output-on-failure --no-tests=error`).
- Extraction is tested with golden files: small sources in `tests/fixtures/*.cpp` (using the real sol2 headers
  from overlunky), expected output in `tests/expected/`, compared with `cmake -E compare_files`
  (`tests/RunGolden.cmake`; register a fixture with `dd_add_golden_test(<name>)` in `tests/CMakeLists.txt`). No
  lit/FileCheck setup.
- Every newly covered binding or callback pattern gets a fixture and a golden file in the same change. When
  output changes on purpose, regenerate the affected golden files and review the diff; never regenerate them to
  hide an unexplained change.
- Pure helper logic (type classification, comment directive parsing) may get GoogleTest unit tests, pinned with
  `FetchContent` (URL + SHA256, `SYSTEM`, `SOURCE_DIR` under `thirdparty/`) like the LLVM package.
- `tools/parity.py` compares the digger output with the old `parse_source.py` results. Run it at the end of
  every step and keep its report free of regressions.
- The output format is frozen in `schema/docs-digger.schema.json` (every field described; the `schema.<name>` tests
  check each golden file with `tools/check_schema.py`). A change to the output fields or their meaning updates the
  schema in the same change and raises `schema_version` (`SchemaVersion` in `src/model.hpp` and the schema's `const`).
- A change is finished when it builds, all tests pass and the quality gate passes.

## When Editing or Creating Code

- Every new function, class, struct, field, enum (and enum value whose meaning is not obvious) gets a one-line
  comment stating its intent: why it exists, not what the code literally does. Put it on the declaration (the
  header for public items).
- Keep Clang AST code in as few files as the plan lists (matchers in `bindings.cpp` and `callbacks.cpp`, AST
  reading in `resolve.cpp`, `usertypes.cpp`, `types.cpp`, `comments.cpp`), so that LLVM major bumps stay contained.
- When adding new source files, list them explicitly in `CMakeLists.txt` (no globbing).
- Use RAII and values; avoid raw owning pointers.
- The code is built without RTTI, like the LLVM libraries it links: no `dynamic_cast` or `typeid`; use
  `llvm::dyn_cast` / `llvm::isa` on Clang AST nodes.
- **PREFERENCE** Slow processing is acceptable, this is documentation parser. Becoming faster is of course
  preferred but can be done in a later plan step. Parallel processing is preferred.
- When committing do not add "Co-Authored By" line.
- **IMPORTANT** For subagents choose faster model such as Sonnet at effort medium or low.
